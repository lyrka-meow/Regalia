# Regalia architecture

## Components

### `regaliad`

`regaliad` owns persistent VPN state and exposes API version 2 over a local Unix
socket. The socket directory is private to the current user, and the socket is
created with mode `0600`.

The daemon currently handles:

- subscription profile lifecycle and atomic refresh;
- server inventory and active-server selection;
- route profile persistence;
- application discovery and per-executable routing rules;
- validation and generation of a sing-box TUN configuration;
- systemd-backed sing-box lifecycle and failure reporting.

### `regalia`

`regalia` is both a numbered terminal interface and a scripting client. It does
not read or modify the state file directly; all operations go through the local
API.

### State

State schema version 1 is stored as JSON with mode `0600`. Updates are written
to a temporary file, synchronized, and atomically renamed over the previous
state file.

Subscription refresh is also logically atomic: a failed download or invalid
payload records the error but does not erase the previous valid servers.

## Local API

Transport: newline-delimited JSON over a per-user Unix socket.

Request:

```json
{"id":1,"method":"status","params":{}}
```

Response:

```json
{"id":1,"result":{"apiVersion":2}}
```

API version 2 currently exposes:

- `status`
- `vpn.connect`
- `vpn.disconnect`
- `apps.list`
- `profiles.list`
- `profiles.create`
- `profiles.delete`
- `profiles.refresh`
- `servers.list`
- `servers.select`
- `routes.list`
- `routes.create`
- `routes.delete`
- `routes.activate`
- `routes.app.set`
- `routes.app.remove`

## Routing model

Every route profile has a default outbound: `proxy` or `direct`. Application
exceptions use absolute executable paths resolved from installed `.desktop`
files. The generated sing-box configuration converts those rules to
`process_path` entries.

Only the local user can access the API and state. The UI-facing daemon remains
unprivileged and delegates only TUN startup and shutdown to the engine bridge.

## Engine lifecycle

Before starting the engine, `regaliad`:

1. builds the configuration from the selected server and route profile;
2. atomically writes it with mode `0600`;
3. runs `sing-box check` with a timeout;
4. asks systemd to start `regalia-engine@UID.service`;
5. records the process ID, start time, state, and diagnostic log tail.

The system service runs as the same numeric desktop UID and receives only
`CAP_NET_ADMIN`. Its `regalia-engine` wrapper:

1. rejects non-private, non-regular, oversized, or differently owned config
   files;
2. accepts only the TUN, DNS, outbound, and `process_path` routing structure
   generated by Regalia;
3. rejects a sing-box binary that is not an absolute, root-owned regular file
   protected from group and other writes;
4. reads the configuration once and passes the same bytes over standard input
   to both `sing-box check` and `sing-box run`;
5. opens the private engine log itself after systemd has dropped to the target
   UID, without following symbolic links.

The systemd sandbox blocks home-directory access, filesystem writes outside
the private runtime directory, device access other than `/dev/net/tun`, extra
capabilities, namespace creation, and uncommon socket families. The service
keeps access to the host network and process table because TUN routing and
`process_path` rules require them.

The accompanying polkit rule authorizes start, stop, and reset-failed
only when the requested unit is exactly `regalia-engine@<subject UID>.service`.

Configuration-changing API operations are rejected while the engine is active,
so the persisted selection cannot silently diverge from the running tunnel.
Stopping sends an interrupt for graceful cleanup; systemd enforces the stop
timeout and tears down the complete service control group. The engine is also
stopped when the daemon exits normally.

## Development fallback

`regaliad --engine-mode process --engine /path/to/sing-box` runs sing-box as a
direct child for isolated development and tests. It does not grant TUN
privileges and is not the packaged production mode.

The next implementation boundary is connection restoration after login and the
QuickShell-facing client integration.
